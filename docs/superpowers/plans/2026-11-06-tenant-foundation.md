# Tenant Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. This plan tracks implementation. The [release board](../../release/status.md) links the verification evidence for each delivered increment.

**Goal:** Establish distinct tenant and school ownership, upgrade the actual starter safely, and provide verified school-context operations for the existing workflows and explicit multi-school provisioning.

**Architecture:** Keep pure hierarchy/ownership rules separate from control-plane identity, durable routing and SQL adapters. Use additive versioned schemas and a resumable maintenance upgrade, preserving legacy identifiers through explicit mappings. All existing business paths converge on verified context and a tenant transaction boundary before multi-school operation is enabled.

**Tech Stack:** Go version/toolchain and dependency versions are authoritative in the current `go.mod`/lockfiles (security upgrade target: Go 1.26.10); preserve the Goravel 1.18 application structure and use the exact framework revision recorded in go.mod. Use database/sql, SQLite/PostgreSQL, React/Wails, Expo and the shared TypeScript API client. Preserve the patched dependency baseline; do not restore the starter's older Go/dependency versions when building upgrade fixtures.

**Spec:** [Tenancy and placement](../../product/tenancy-and-placement.md), [production scope](../../product/production-scope.md), [master backlog](2026-11-06-production-release.md). The tenancy specification governs conflicts with starter school-as-tenant assumptions, including the master plan's shorthand instruction to reuse `access.Principal`.

## Global constraints

- “Tenant is the first-release placement unit.” All organizations/schools of a tenant share one active data placement.
- “Identifiers do not encode hierarchy, location or physical database.” New scope and subject IDs are canonical random UUIDs; existing business IDs remain byte-for-byte unchanged.
- “For the initial migration, keeping all authorization grants in the control database avoids an eventual-consistency authorization decision.” Hierarchy remains authoritative in the data plane; context indexes cannot expand access while stale.
- “A nullable scope is not interpreted as wildcard access.” Every owner has an explicit kind.
- “Same-driver moves ship before SQLite↔PostgreSQL typed conversion, which is a separately verified capability.” This plan enables no move command.
- Domain/application/contracts import no HTTP, SQL or Goravel packages. Shared ID/access contracts remain framework-free. Cross-module operations use public contracts and borrow the same scoped transaction.
- Existing migration IDs, SQL statements, pool markers, receipt rows and historical schema signatures are immutable. Never silently replace `SchemaUp` behind a previously applied signature.
- Test commands below are instructions for implementation, not evidence that this planning pass ran them. Missing PostgreSQL/blob/browser prerequisites leave their gates open.

## Bounded increment and delivery gates

This plan refines TEN-02, TEN-03 and the enabling CTX-01/02 slice, with the minimum TEN-04 transaction/routing work they require. It has two independently reviewable boundaries: **A (Tasks 1–2)** is a pure typed domain model with no runtime behavior change; **B (Tasks 3–11)** is the integrated compatibility/upgrade and real existing-workflow slice. Do not call TEN-03 or enable multi-school provisioning after boundary A alone.

Boundary B covers the existing student register, enrollment placements, generic module work lists, files, login/membership commands, native worker and clients. It does not complete organization reparenting/lifecycle administration, arbitrary role editing, teams, location management, curricula, hierarchical configuration, group aggregates, person linking, exports/reporting domains or tenant moves. Unsupported scope/action combinations return explicit errors; no placeholder screen or generic workspace claims completion. TEN-04 strict suspension/move controller acceptance remains open beyond the transaction gate primitives exercised here.

## Review focus

1. A second school added to a formerly single-school tenant must not make an old admin implicitly group-wide or make a legacy session choose a school (Tasks 5, 9).
2. Old binaries do not understand new gates: migration maintenance must stop/fence their DB and file access, not rely on a new readiness flag they never read (Tasks 4, 11).
3. Document checksums include the legacy path; renaming a blob without verified rewriting corrupts its integrity contract (Task 8).
4. A worker may already hold an event lease when upgrade begins; preserve attempts/delivery receipts and prohibit concurrent old/new consumers (Tasks 4, 7).
5. A switch can succeed on the server after the client loses the response; original context remains correctly labeled, and stale success/error/401 callbacks cannot affect a newer context (Tasks 9–10).

## Locked contracts for Tasks 2–10

Use `scope` below as the import alias for new `platform/scope`; use `access` for existing `platform/access`. IDs use distinct opaque generic instantiations for tenants, organizations, schools, campuses, locations, teams, curricula, subjects, memberships, pools and sessions. Canonical UUID v4 parsing, text encoding and zero checks are shared. Entity kinds cannot be interchanged or constructed by casting untrusted strings. Legacy slugs and business record IDs retain their existing representation.

- `scope.Selection { Tenant TenantID; Organization OrganizationID; School SchoolID; Campus CampusID; Team TeamID }`: requested narrowing; empty optional fields mean absent selection only.
- `scope.Owner { Kind OwnerKind; Tenant TenantID; Organization OrganizationID; School SchoolID; Campus CampusID }`: exactly one declared ownership level and consistent parent fields. The implementation exposes read-only accessors and derives ownership from a resolved chain. Supported owners in this increment are tenant/topology and school/business; campus ID types/ancestry are available but campus-restricted business grants are denied until a resource supports them.
- `scope.Chain { Tenant TenantID; Organization OrganizationID; School SchoolID; Campus CampusID; HierarchyVersion uint64; Active bool }`: authoritative resolved ancestry. Team selection returns `unsupported_scope` in this increment; membership is not a grant.
- `tenancy/contracts.Directory.Resolve(ctx context.Context, selected scope.Selection) (scope.Chain, error)`: called by trusted verification; reads through a tenant maintenance-aware scope transaction, never a caller-selected raw pool.
- `access.Authenticated { Subject scope.SubjectID; Membership scope.MembershipID; Session scope.SessionID; Tenant scope.TenantID }`: trusted authentication output, not an HTTP body. `access.Verified` has private fields and read-only `Subject()`, `Tenant()`, `Selection()`, `GrantVersion()`, `PlacementEpoch()`, `Locale()` methods; zero value is invalid.
- `access.Authorizer.Verify(ctx context.Context, who Authenticated, selected scope.Selection) (Verified, error)` and `Require(ctx context.Context, verified Verified, action string, owner scope.Owner) error`: `Verify` loads current authority and full ancestry; `Require` checks current grant version, exact ownership and operation. Implementation stays framework-free over authority/directory/placement ports. Only trusted composition/authentication code can request verification; no `UnmarshalJSON` for Verified.
- `platform/database.Placement { Tenant scope.TenantID; Pool scope.PoolID; Epoch uint64; State PlacementState }`; `Catalog.ResolvePlacement(ctx context.Context, tenant scope.TenantID) (Placement,error)`: read-only durable lookup, error on absent/inactive/unknown pool/schema.
- `access.UnitOfWork.Run(ctx context.Context, verified Verified, mode TransactionMode, work func(context.Context) error) error`, with `ReadOnly` and `ReadWrite`. SQL implementation in `platform/database/unit_of_work.go` carries a private `{tenant,pool,epoch,tx}` handle in the callback context; only SQL adapters inspect it. Public module contracts never take `*sql.Tx` or Pool. Nested calls must match tenant/epoch and must not promote a read-only transaction.
- Existing public use-case methods replace loose `school,actor` arguments with Verified and typed command/query: `students.Service.Register(ctx, verified, RegisterCommand)`, `students.Service.Lookup(ctx, verified, id string)`, `students.Service.List(ctx, verified, ListQuery)`, `students.Service.Update(ctx, verified, UpdateCommand)`, `students.Service.Archive(ctx, verified, ArchiveCommand)`; return current DTOs/errors. `RegisterCommand { GivenName, FamilyName string }`, `ListQuery { Limit, Offset int }`, `UpdateCommand { ID string; ExpectedVersion int64; GivenName, FamilyName string }`, `ArchiveCommand { ID string; ExpectedVersion int64 }` live in `modules/students/application/commands.go`. Owner comes from verified selection, never client `school` strings. `students/contracts.Directory.Lookup(ctx context.Context, verified access.Verified, id string) (Student,error)` remains the enrollment boundary; no gratuitous method rename. `placements.Record/Withdraw/List`, `workspace.Service.Get/List/Create/Update`, and `documents.Files.Upload/Download` likewise take `(ctx, verified, commandOrQuery)`; commands contain their existing business inputs only. Persistence ports take verified owner and the callback transaction context; actor always comes from Verified.

The type is a trusted-code discipline, not a cryptographic capability; authoritative database checks remain mandatory. Public ports deny zero/fabricated/expired scope. Architecture tests prohibit transport decoding into Verified and prohibit SQL adapters bypassing the shared UoW.
